# The gate, and what each failure actually means

```bash
cd packages/design-system && npm run check
```

The steps, in order, live in `packages/design-system/scripts/gates.mjs` — one
list, from which both `check` and `check:ci` are derived. Print it rather than
remembering it:

```bash
npm run check -- --list             # every step, its lane, what it is for
npm run check -- --timings          # where the 37 seconds went
npm run check -- --from lint:rules  # resume after fixing one
npm run check -- --serial           # one stream of output, for reading live
```

The steps run in four lanes at once, so the output arrives per step as it
finishes rather than live; a failure prints its whole output.

Node is not on PATH in a non-interactive shell here: `. packages/design-system/scripts/node-path.sh` first.

## Failure playbook

| Step | What it really means | First move |
|---|---|---|
| `gen-registry:check` | Source and registry disagree, or a token/variant is undefined | `npm run gen-registry`, then read the diff. Never hand-edit the registry |
| `lint:rules` | The custom linter: raw px, tonal stop instead of semantic role, upward import, raw form control, icon button without aria-label, dead CSS, file > 600 lines | Fix the code. The `ALLOW` map is known debt to shrink, never a place to add |
| `contrast` | A WCAG pair regressed in one theme | Fix the token, not the test. Accepted misses may only improve |
| `context` | `AGENTS.md` + `component-index.md` exceed the token ceiling every task pays, or a registry entry is over the per-entry ceiling an agent pays to fetch it | Trim payload (shorter `use` sentences, shorter examples) before raising the ceiling, and write the reason if you do raise it |
| `check:spec` | A screen spec names a component/prop/value that does not exist | Fix the spec, or the system, not the validator |
| `test` | Examples must render and be axe-clean; every advertised variant must land as `data-*` | A variant that stopped forwarding still compiles and silently loses all styling |
| `eval` | A candidate solution stopped using the system | Read which dimension dropped: `required-used`, `no-hand-rolling`, `style-hygiene` |
| `size` | Gzipped app bundle over budget | The `visual-*` bundle is excluded on purpose (QA artifact) |
| `visual` | Pixels differ from the committed baselines | See below |

## Visual diffs: look before you accept

`npm run visual:update` rewrites baselines. Before running it, open the
`actual`/`baseline` pair from `visual/.diff/` and decide which you are seeing:

- **A real change** (padding, colour, layout moved) — accept only if intended.
- **Rasterisation drift** — every case shifts by ~1px, symmetric in light and dark,
  0.3-0.8% of pixels, and no CSS changed. Usually a new Chromium after a clean
  install. Accept, and say so in the changelog.
- Baselines are machine-specific by design. A diff on another machine is "look at
  this", not "you broke it".

## Gotchas

- **The gate is also wired to hooks**, so it is not optional: PostToolUse lints every
  `.ts/.tsx/.css` edit and blocks the edit, the Stop hook blocks ending a turn while
  red, `.githooks/pre-commit` runs the whole thing per commit (`git config core.hooksPath .githooks`).
- **A green hook can mean it never fired.** When you change hook wiring, prove it
  rejects: inject a violation (a raw hex in a component CSS), confirm exit code 2, revert.
- **`npm run visual` needs a real Chromium**: `npx playwright install chromium` after
  a clean install, or the step dies with "Executable doesn't exist".
- **semgrep, where a gate runs it, is a brew binary** and not an npm dep. It sits
  at `/opt/homebrew/bin/semgrep`; a non-interactive shell may not have it on PATH.
- **`npm run lint:dead` (knip) is triage, not a gate.** Do not blind-delete its
  "unused export" hits; many are used internally and only need the `export` dropped.

## Start from `checks.json`, not from memory

`checks.json` at the repository root is the generated map of everything that can
be verified: every check in every package, whether a gate runs it, and what
question it answers — taken from the check's own leading comment, so it cannot
describe something the code does not do.

Read it before deciding what to run. It is regenerated by `npm run gen:checks`
and verified in the design system's gate, so an entry that is missing means the
check is missing, not that the map is stale.

The division it serves: the code decides what is TRUE, and you decide what to DO
about it. Do not re-derive from package.json what this file already states.
